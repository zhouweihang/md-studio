# ADR-007: 搜索暖路径使用内存快照缓存

> Status: Accepted | Date: 2026-10-23 | Deciders: 项目所有者 | 关联 RFC: RFC-006 §4.4 | Supersedes: ADR-004 | 影响：搜索延迟、内存占用、外部编辑可见性

## Context

ADR-004 选择「每次查询实时扫描、不建索引」。实测 1,001 篇、约 0.32 MB 正文，release 313.01 ms、debug 330.97 ms：debug 只慢 6%，说明耗时在每次查询重新遍历目录、`canonicalize`、读取全文的系统调用上，而不是字符串处理。按此线性关系，10k 档约 3 s、50k 档约 15 s，无法满足「输入即出结果」的体验。

约束：

- 文件系统仍是唯一事实源（ADR-003）；外部编辑器随时可能改动文件。
- 保存必须继续用内容 revision 做乐观并发（ADR-005），缓存不得参与冲突判定。
- 单工作区上限从 10,000 提升到 50,000（RFC-006 REQ-028），单文件仍限 5 MiB。
- 不引入数据库、迁移或跨会话持久化状态。

## Decision

1. 新增进程内**只读**快照 `path → { text, mtime, size, title, last_used }`，仅在当前会话与当前工作区内有效。
2. 打开工作区后立即在后台预热（`spawn_blocking`，64 篇一批），查询不等待预热完成；未就绪时回退实时扫描。
3. **预算内全量缓存正文**；默认上限 256 MB，可由设置项或 `MDSTUDIO_SEARCH_CACHE_MB` 覆盖。超过预算按 LRU 淘汰，被淘汰的笔记回退读盘，结果不变。
4. 查询在内存中并行扫描，借用 `Arc<str>`，不复制正文；命中仍受 50 条、每篇 3 条上限约束。
5. 失效：优先由文件监听增量更新（ADR-009）；监听失败时，查询前对涉及的笔记做 mtime+size 校验。
6. 快照只服务读路径；`write_note` 仍然先读盘比对 revision，冲突语义不变。
7. **取代 ADR-004**：保留「实时扫描」作为冷路径与降级路径，但不再作为唯一实现。

## Alternatives

- **继续实时扫描（ADR-004 原方案）**：零内存成本、外部修改天然可见，但延迟随文件数线性增长，10k 档已达数秒，无法达到 RFC-006 的 SLO。
- **SQLite FTS / 持久化倒排索引**：查询最快，但引入数据库、迁移、双写一致性与外部修改失效问题，与 ADR-003 的定位冲突。
- **只缓存元数据（mtime/size）**：省内存，但仍需读盘，无法解决主要瓶颈。
- **只做并行不缓存**：1k 档可降到 60–120 ms，但 10k/50k 档仍受 I/O 限制，且每次查询都重复付出同样的磁盘成本。
- **缓存所有内容且不设预算**：10k × 5 MiB 理论上限 50 GB，会耗尽内存；必须有预算与淘汰策略。

## Consequences

- 正：10k 档暖查询进入毫秒级（目标 p95 ≤ 20 ms + 0.10 ms/MiB 已缓存正文，即带宽 ≥10 GB/s；2026-10-25 由 RFC-006 REQ-024 修订，原绝对 20 ms 阈值废止），50k 档具备可行性；搜索结果不再随磁盘抖动。
- 正：外部修改通过监听 + mtime 校验保持可见；缓存失效只降速、不改结果。
- 正：快照不持久化，退出即释放，不引入迁移与清理问题。
- 负：内存占用最多 256 MB；50k 档接近预算上限，LRU 淘汰成为常态。
- 负：新增预热成本（10k 档 ≤3 s 后台时间）与监听复杂度。
- 负：快照与磁盘之间始终存在极短的可见性窗口；靠监听去抖与 mtime 校验收敛，不做强一致。
- 风险：Windows Defender、网络盘、超大单文件会显著降低预热与命中率；这些场景以「不慢于实时扫描」验收，并触发 ADR-010 评估。
- 风险：ADR-003 的「不缓存正文」表述需要限定为「不建持久化正文库」，见 ADR-003 的 Amendment。
