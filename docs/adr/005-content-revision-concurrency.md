# ADR-005: 用内容 revision 做乐观并发，不使用文件锁

> Status: Accepted | Date: 2026-10-23 | Deciders: 项目所有者 | 关联 RFC: RFC-003 §4.1/§4.2 | 影响：读写命令契约、冲突检测可靠性、跨平台行为

## Context

RFC-002 的重命名/删除让应用开始承担「整理文件」的职责，但保存仍是最后写入获胜。用户在 Typora/VS Code 中修改同一文件后，MD Studio 的下一次自动保存会静默覆盖外部内容。需要一种在保存前发现变更的机制，同时保持文件系统是唯一事实源（ADR-003）。

约束：

- 文件可能被外部编辑器原子替换、改写或删除。
- Windows/macOS/Linux 的文件时间精度与语义不一致。
- 笔记最大 5 MiB，读取整篇成本可接受。
- 不引入后台索引、数据库或跨平台文件锁服务。

## Decision

1. `read_note` 返回 `{ content, revision }`；revision 是对文件原始字节做 FNV-1a 64 位哈希后的 16 位十六进制字符串。
2. `write_note` 接收 `expected_revision`，写入前重新读取磁盘字节并计算当前 revision；不一致返回 `conflict:` 错误，不写入。
3. 前端用 `revisionRef` 保存当前 revision；每次成功写入用返回值更新；改名不改变 revision。
4. 冲突不做合并，只提供「重新载入磁盘版本」或「用本地内容覆盖」。
5. 不引入 OS 文件锁；接受检查与写入之间的 TOCTOU 窗口。冲突检测是数据保护，不是安全边界。

## Alternatives

- **mtime + size**：实现简单，但时间戳精度有限（FAT 2s、网络盘更差），外部修改可能保持相同大小与时间戳；误判/漏判都不可接受。
- **保存时比较完整旧内容**：无哈希碰撞，但每次保存要额外传输最多 5 MiB 的期望内容；前端/IPC 负载更大。
- **OS 文件锁（flock/LockFileEx）**：跨平台语义不同，编辑器原子替换会绕过锁，锁文件还会污染工作区；对本地写作工具过重。
- **继续最后写入获胜**：实现成本最低，但会静默丢失外部修改，违反本 RFC 的目标。
- **三方合并**：需要共同祖先与冲突标记 UI，复杂度远超当前单稿模型。

## Consequences

- 正：保存前能发现外部修改；冲突时本地内容不丢，用户可显式选择。
- 正：revision 不落盘、不建索引，不增加持久化状态。
- 正：哈希基于内容，不受文件时间精度影响。
- 负：每次读取/保存多一次字节哈希；5 MiB 文件的成本可接受。
- 负：FNV-1a 非加密哈希存在理论碰撞；仅用于变更检测，不作为安全校验。
- 负：检查与写入之间仍有极小 TOCTOU 窗口，极端并发下仍可能覆盖。
- 风险：外部程序在保存瞬间改写文件仍可能漏检；未来若需要强一致，再评估文件锁或版本化存储。
