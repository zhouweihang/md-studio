# ADR-009: 用文件监听维护搜索快照失效

> Status: Accepted | Date: 2026-10-23 | Deciders: 项目所有者 | 关联 RFC: RFC-006 §4.6 | 影响：外部修改可见性、后台线程、跨平台监听差异

## Context

ADR-003 明确「不监听文件系统变化（MVP）」，backlog B1-3 一直保留该能力。引入内存快照（ADR-007）后，快照会与磁盘产生偏差：用户很可能同时在 Typora、VS Code 或 Git 中修改同一批文件。若只在查询时全量 `stat`，10k 档每次查询要付出数千次系统调用，抵消快照收益；若完全不校验，外部修改在搜索中不可见，违背「文件系统是唯一事实源」。

约束：

- 快照失效只允许降低速度，不允许返回错误结果。
- 不引入后台常驻服务或跨平台守护进程。
- 网络盘、OneDrive、权限受限目录上的监听可能不可靠。
- Windows 上编辑器常用「临时文件 + rename」原子保存，事件形态与直接写入不同。

## Decision

1. 使用 `notify` 递归监听当前工作区，监听生命周期与工作区绑定，切换工作区时重建。
2. 只处理 Markdown 文件与目录事件；隐藏目录、`node_modules`、`target`、`dist`、`build` 继续忽略，避免构建产物触发风暴。
3. 事件去抖 300 ms 后合并处理：`create/modify` 重读该文件并更新快照，`remove` 删除条目，`rename` 删除旧键并插入新键。
4. **监听是 best-effort**：初始化失败、事件溢出、连续读取失败时把快照置为 `Degraded`；此后查询前对涉及的笔记做 mtime+size 校验，不一致则重读。
5. 手动刷新执行全量对账：重新遍历工作区并重建快照，作为任何异常状态的最终兜底。
6. 原子保存必须通过 `rename/create` 事件被识别；集成测试覆盖该路径。
7. 监听不参与保存与冲突判定；`write_note` 的 revision 校验保持不变（ADR-005）。

## Alternatives

- **完全不监听，仅查询时校验**：实现简单，但 10k 档每次查询数千次 `stat`，在 Windows 上可达百毫秒级，抵消大部分快照收益。
- **定时轮询**：行为可预测，但后台 I/O 持续消耗，且可见性延迟取决于轮询周期。
- **前端 `chokidar` 监听**：WebView 无法直接访问文件系统，且需要 fs 权限，违背安全模型。
- **平台专用 API（ReadDirectoryChangesW / FSEvents / inotify）**：控制力最强，但要维护三套实现与差异测试，超出当前只支持 Windows 的范围。
- **放弃外部修改可见性**：与 ADR-003 的事实源定位冲突，不可接受。

## Consequences

- 正：外部编辑在数百毫秒内进入快照，搜索保持「所见即磁盘」。
- 正：查询路径不再需要全量 `stat`，快照收益成立。
- 正：同时补齐 backlog B1-3，文件树也可复用同一事件流做增量更新（后续）。
- 负：新增后台线程与跨平台监听差异；Windows 之外的可靠性未验证。
- 负：事件风暴（批量 Git 操作、安装依赖）可能造成短时抖动，必须去抖与过滤。
- 风险：网络盘/OneDrive 上监听可能完全失效，此时永久 `Degraded`，搜索仍正确但更慢。
- 风险：事件丢失导致的陈旧条目只能靠 mtime 校验或手动刷新发现，不做强一致。
