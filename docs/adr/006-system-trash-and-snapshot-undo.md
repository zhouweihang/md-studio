# ADR-006: 删除使用系统回收站，撤销使用会话内内容快照

> Status: Accepted | Date: 2026-10-23 | Deciders: 项目所有者 | 关联 RFC: RFC-004 §4.1/§4.2 | 影响：删除命令契约、撤销语义、跨平台行为

## Context

RFC-002 把删除实现为 `fs::remove_file`，误删不可恢复（backlog B1-7）。用户期望「删除」是可撤回的常规操作，而不是不可逆的数据销毁。可选方向有三类：

- 把文件移入应用自己的暂存目录，由应用管理生命周期。
- 直接调用系统回收站，由操作系统管理。
- 只做软删除标记（重命名/索引），原路径不再可见。

约束：

- 文件系统是唯一事实源（ADR-003）：不建数据库、不缓存正文、不复制第二份磁盘副本。
- 单窗口、单笔记会话；笔记上限 5 MiB。
- 需要跨平台（Windows 优先，macOS/Linux 兼容）且不引入平台专属代码。
- 系统回收站没有统一的「按路径恢复」API，恢复不能依赖平台。

## Decision

1. 删除通过 `trash` crate 移入系统回收站；失败则删除失败，文件保持原位。
2. `delete_note` 返回 `{ path, content }`，其中 `content` 是删除前读取的 UTF-8 文本快照（>5 MiB 或非 UTF-8 时为 `null`）。
3. 撤销只覆盖最近一次删除且仅在当前会话内：前端持有快照，`restore_note` 把文本写回原相对路径。
4. 恢复拒绝覆盖已存在文件，沿用路径校验与 5 MiB 限制。
5. 不扫描、不枚举、不清空系统回收站；更早的文件由用户通过操作系统找回。

## Alternatives

- **应用内 `.trash/` 目录**：可在应用内浏览与恢复，但会在工作区留下隐藏目录、复制正文，破坏「文件系统即事实源」与「无第二份副本」的约定；还需要清理策略。
- **只做软删除（重命名为 `.deleted`）**：恢复容易，但文件仍占工作区、会被扫描/搜索逻辑特殊处理，用户也难以理解；本质上仍是自制回收站。
- **系统回收站且不提供撤销**：实现最小，但删除后要跳出应用去回收站翻找，不满足「撤销入口」。
- **系统回收站 + 平台恢复 API**：语义最完整，但 Windows/macOS/Linux 没有统一契约，需要三套平台代码与权限，维护成本高。
- **持久化删除历史**：跨重启可撤销，但需要数据库/日志与清理策略，超出当前单稿模型。

## Consequences

- 正：误删可从系统回收站找回；删除后立即撤销不需要离开应用。
- 正：不新增磁盘目录、索引或平台专属代码；`trash` 负责三平台差异。
- 正：恢复沿用现有路径校验，不会写出工作区或覆盖他文件。
- 负：撤销只覆盖最近一次、当前会话；重启后只能去系统回收站找。
- 负：>5 MiB 或非 UTF-8 文件可删除但没有应用内撤销。
- 负：恢复只还原内容与路径，不还原 mtime/ACL；恢复后的文件 revision 是新值。
- 风险：`trash` 依赖平台回收站可用性（如精简版 Linux 桌面）；失败路径已明确报错，不会静默删除。
