# ADR-004: 全文搜索用 Rust 实时扫描，不建索引

> Status: Accepted | Date: 2026-10-23 | Deciders: 项目所有者 | 关联 RFC: RFC-002 §4.3 | 影响：搜索命令、性能上限、未来索引切换点

## Context

RFC-002 需要按 Markdown 正文搜索。当前前端只持有 `NoteEntry[]`（路径、标题、修改时间），没有正文；若在 UI 层搜索，有两种做法：逐文件 `invoke('read_note')`（N 次跨进程往返）或把全部正文读入内存（大工作区内存与启动成本高）。文件系统是唯一事实源，且 ADR-003 明确不维护正文数据库。

约束：

- 单工作区最多 10,000 篇、单文件 5 MiB（RFC-001 §4.1）。
- 搜索必须可取消/可丢弃旧结果，不能阻塞 UI 线程。
- 不引入新的持久化状态与迁移成本。

## Decision

1. 新增 Rust 命令 `search_notes(root, query)`，在 `spawn_blocking` 中执行。
2. 复用 `list_notes` 的扫描结果，逐篇读取 UTF-8 正文，按行做大小写不敏感的子串匹配。
3. 返回 `SearchHit { path, title, line, preview }`；每篇最多 3 条，总计最多 50 条，命中即停。
4. 不建 SQLite FTS、不建内存倒排索引；查询变化时前端用取消标记丢弃过期响应。
5. 切换阈值：工作区文件数 > 5,000 或单次搜索超过 200ms（在目标机测量）时，另开 ADR 评估派生索引。

## Alternatives

- **前端逐文件读**：每篇一次 IPC，10,000 篇会产生大量往返；把扫描/取消逻辑放进 UI，测试需要 mock 大量平台调用。
- **前端一次性读入所有正文**：内存占用与启动延迟不可控，且要自己维护缓存失效。
- **SQLite FTS5 索引**：搜索最快，但引入数据库、迁移、外部修改失效与双写一致性；与 ADR-003 的「文件系统唯一事实源」冲突。
- **启动时构建内存索引**：每次启动 O(N) 读盘，工作区大时启动变慢；仍需处理外部修改。
- **调用系统 grep/ripgrep**：平台依赖强，Windows 交付不可控，且无法直接生成结构化行号/片段。

## Consequences

- 正：无新增依赖、无索引失效、无迁移；外部编辑器改动立即被搜索到。
- 正：路径校验与文件读取复用同一 Rust 边界，安全模型不变。
- 正：搜索在阻塞线程池执行，不冻结 WebView。
- 负：每次查询 O(文件数) 读盘；大工作区/慢磁盘上延迟线性增长。
- 负：只做字面子串，不支持正则、模糊、排序相关性。
- 风险：命中上限会截断结果，用户可能看不到靠后的匹配。缓解：UI 明确显示「最多 50 条」；超过阈值时按 ADR 切换索引。
